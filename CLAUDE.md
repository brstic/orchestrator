# Orchestrator — working notes for Claude

A 3D office in which real Claude Code CLI sessions (in tmux) are employees. pnpm monorepo, Node ≥ 22.18 runs the TypeScript sources directly.

## Read before working
1. `docs/STATUS.md` — what is shipped, what is in progress, known problems. **Start here.**
2. The active plan under `docs/plans/` (currently `UPDATE-central-office.md`).
3. `docs/HANDOVER.md` — the whole loop for someone new to this repository: what you need, test, commit, push, deploy. `docs/OPERATIONS.md` — where the server and clients run and how each is updated (`pnpm deploy:server`). `docs/DEVELOPMENT.md` — how to build and test, and the rules that protect the live office.
4. The page of the feature you are about to touch, where there is one (`docs/MEMORY.md`, `docs/VAULT.md`, `docs/ACCOUNTS.md`, `docs/ARCADE.md`, `docs/CHARACTER.md`, `docs/MESSAGE-PERSON.md`, `docs/ATTACHMENTS.md`, `docs/SIGN-IN.md`, `docs/HELD-REQUESTS.md`, `docs/SURROUNDINGS.md`, `docs/TASKS.md`, `docs/TEAM-LEAD.md`, `docs/MOVE.md`, `docs/RELEASE-GATE.md`, `docs/UI.md` — the look every window is being moved to, read it before changing any window; `docs/README.md` is the map). A feature of that size gets such a page in the same piece of work.
5. `docs/DECISIONS.md` — why things are the way they are. Add an entry when you decide something a later reader would otherwise have to guess.

## Keep the docs true (standing rule)
Every change that alters behaviour, finishes or starts a plan item, or changes how to build/test/ship **updates the Markdown in the same piece of work**: tick the plan item, update `docs/STATUS.md`, add a line to `docs/CHANGELOG.md`, and touch `ARCHITECTURE.md` / `SECURITY.md` / `INSTALL.md` when their subject changed. Docs describe what the code does now, not what was intended. If something was not verified, say so there.

## Checking a change
`pnpm check:changed` is the fast loop while you work: it typechecks (only when a typechecked `.ts` changed) and runs the unit tests *beside* what you touched — the `test/` folder of each workspace a changed file belongs to — plus any changed `tests/e2e` file. It runs the tests of the packages you changed, not of the packages that depend on them, so it is a quick gate, **not** a replacement for `pnpm test:all` before shipping. `--base <ref>` measures a whole branch (e.g. `pnpm check:changed --base origin/main`); `--dry` prints the plan.

**Hit every surface.** A change is not done until you have thought about each of these and said in the work which it touches and how it was checked (or why not):
- **Roles** — visitor, colleague, owner. A control shown, hidden or disabled per role is checked as each role, not only as owner.
- **Shared vs personal** — a shared employee on the office's machine, and a member's own employee on their own computer (member rooms, privacy of their tasks/feed).
- **Local vs server office** — one machine, and the office running on the server behind the TLS door (deploy is the owner's call; see `OPERATIONS.md`).
- **Desktop vs browser** — the Electron app and a plain browser tab (preferences, autoplay, clipboard differ between them).
- **Every runtime** — interactive `claude` in tmux (primary), the SDK-managed worker, and the Codex-managed worker (`docs/CODEX.md`).
- **A bug fix starts with a failing test** — one that fails for the bug, then passes with the fix.

## Hard rules
- Product text is English. The owner writes Serbian; answer them in Serbian.
- Never run the real `claude` CLI or `tests/real/*` without being asked: it spends the owner's Claude usage. Tests use `tests/fixtures/fake-claude.mjs`.
- Never package (`scripts/package.mjs`) into `release/` while `release/Orchestrator.app` is running — package with `--out release-next`, check it (`smoke-package.mjs --out release-next`), then `node scripts/update-mac-app.mjs` closes the owner's app, swaps the build in and opens it again — only if it was running (the owner's standing word of 2026-11-12: "close the app for me and start the new one, every time"; and of 2026-11-27: an app they had closed stays closed). The app is closed by that script, never killed; never kill the owner's tmux server or `orch-*` sessions; no `pkill`/`killall`.
- Workers run in Claude Code's bypass-permissions mode only as the autonomy level **Unrestricted** — the owner's decision of 2026-11-11 and their default (`docs/DECISIONS.md`, "Unrestricted"; `docs/SECURITY.md`). Never add the flag any other way, never for SDK-managed workers, never `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS`; the project's deny rules and the fence around the office's own files stay in front of every level, and Claude Code's bypass warning is the owner's to accept — and since 2026-11-13 the owner has accepted it once for all: the office answers it by itself for an employee an owner put on Unrestricted, on the office's own machines (their word: "this too should pass by itself"; the switch `acceptStartPrompts` in Settings → Employees, `docs/DECISIONS.md`, "The office answers Claude Code's start-up questions"). Never widen that: not on a member's own computer, not for any other level, and never switch it back on for an owner who switched it off. The office's high-risk gate stands in front of every level too, except where the owner switched it off for Auto or for Unrestricted (two switches in Settings → Employees; the owner's decision of 2026-11-11, `docs/DECISIONS.md`, "Unrestricted employees are not held…") — never switch either for them, and never make "off" the default. Codex-managed workers run with Codex's own approvals off because they have nothing to approve: no shell, no web, writes only to a private scratch folder, their folder only through the workspace tools (`docs/CODEX.md`) — never give them a shell or native writes in the folder without structured approvals and the high-risk gate, and keep the runner's stop (`forbidden`). No unauthenticated remote terminal access. Nothing mocked may be presented as a product feature.
- **This repository is public.** Nothing that belongs to the office we run goes into a tracked file, a commit message or an issue: no real address, port or login (those are in `docs/private/` and `scripts/deploy.local.env`, git-ignored), and also no customer, no person's name, no name of a team's own product, and no text copied from a live session — a prompt or a terminal that goes into a test is rewritten first. Write "an owner", "a colleague", "the server".
- Commit or push only when asked.
